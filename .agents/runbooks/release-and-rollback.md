# 发布与回滚手册

## 先识别发布域

| 发布域 | 主要风险 | 正确回滚方式 |
| --- | --- | --- |
| 模型配置 | 节点配置变化、服务重启、链路中断 | 以历史修订为目标创建新发布，不改写历史 |
| 用户授权 | 访问主体变化 | 提交反向授权变更并形成新的可审计任务 |
| Agent | 收敛逻辑和协议兼容 | 将已知良好的字节设为当前产物，再创建新的发布单 |
| Xray | 数据面兼容、进程健康、链路中断 | 执行失败时本地恢复原字节；人工回退需创建新的发布单 |
| Console | API、数据库、嵌入资源和控制面可用性 | 按 `console-deployment.md` 回滚二进制；先确认数据库兼容 |

不要为了复用操作流程合并这些发布域。一次 Console 部署不会自动更新节点 Agent 或 Xray；配置发布与授权发布的风险和代价也不同。

## 通用发布门槛

发布前必须能够回答：

- 发布对象和不可变标识是什么？
- 影响哪些节点、用户、链路或控制面实例？
- 灰度对象如何选择，成功信号是什么？
- 什么条件会暂停、熔断或回滚？
- 回滚会产生新的审计记录，还是替换宿主机二进制？
- 新旧协议、配置和数据库是否兼容？
- 哪些检查已实际运行，哪些因环境限制未运行？

没有明确答案时只做预检，不开始外部变更。

## 配置发布

设置页的「无人值守发布」默认开启。发起发布后，沿用现有波次完成判据，上一波成功即开放下一波，
不等待人工确认，不增加观察窗口或额外探测；任何执行错误仍按原逻辑暂停。关闭此设置后恢复破坏性
波次的人工确认。保存立即生效，不生成修订或发布单，也不会恢复已经暂停的发布。

1. 确认草稿基线和目标修订，检查预览产物与影响范围。
2. 审查破坏性操作、波次、节点隔离和授权差异。
3. 从低风险灰度开始，观察下发、收敛、健康和拨测结果。
4. 只有当前波次满足成功判据才继续；失败或状态不确定时暂停。
5. 回滚时选择已知良好的历史修订创建新发布，保留原发布和失败事件。

「Xray 进程交接 Beta」为全局运行设置，默认关闭，仅系统管理员修改。创建配置单时把
restart/handoff 策略冻结到每台目标的 desired_structure，并原样传递到隔离补偿工单。
关闭时不能热更新的变更走重启；开启时优先走交接。Agent v40 起，交接能力或运行态不足时允许
经过完整校验的直接重启降级，并记录具体原因；v39 及更早版本保持原来的拒绝行为。策略字段仍
按批准时冻结；升级到 v40 会启用其可用性恢复规则，包含已有 handoff 工单。含新策略的 Xray 配置工单仅向
协议 >=37 的 Agent 下发，领取事务先检查能力，不为旧 Agent 写入 dispatched 状态；授权、
历史工单和证书续期仍走既有兼容路径。部署已有库前先审查兼容 SQL 和迁移校验和。

配置发布的 `ApplyXray` 优先使用共享分类器允许的原进程热更新：仅路由规则与普通出站增删，
且 API、inbound、DNS、policy、balancer、探测和其它启动配置均不变。
路由表沿用上游 `AddRule(shouldAppend=false)` 一次提交完整 `routing` 配置，包含规则与
均衡器；均衡器重建后继续读取原有 Observatory 数据。手动覆盖和轮转索引按上游替换语义
重置，不承诺保留对象运行态。Agent 不再追加新表后逐条删除旧规则；端点别名过渡也提交
完整路由配置。配套 Xray 声明 `atomic-routing-reload-v1`；Agent 在任何热切换操作前读取
运行进程的 `/proc/<pid>/exe version` 并核对进程身份与 API 监听，不能只检查磁盘上已安装的
二进制。缺少能力时按已批准的交接/重启策略处理。构建失败不改变已发布快照。
升级顺序为 Agent → Xray；旧 Agent 仍使用多次增删 RPC，仅更新 Xray 不能消除混表窗口。
沿用原有 `AddRule`/`RemoveRule` 协议，不提供跨 RPC 的事务语义。热更新成功后原子提交
配置检查点，不启动候选进程。规划与 Agent 使用同一个分类器；入站增删或替换始终走代际
交接（Beta 开启时）或重启（关闭时），不先通过非事务性的 gRPC 操作删除旧 inbound。
热更新失败按已批准策略继续；v40 的能力降级必须记录原因和实际结果，不能伪装成保留连接的交接。
运行代必须明确支持 `tcp-handoff-udp-reset-v1` 和 `config-listener-handoff-v1`，但不要求新旧 `api`、`metrics`、完整
`inbounds` 或 splice 模式相等。候选清单根据目标配置和完整动态转发快照构建：共有 TCP
监听在 socket 选项不变时继承 FD；选项变化则创建新 socket，而不是跳过继承摘要检查。
新增监听自行绑定，删除的监听不再要求候选注册。候选代接收新连接，旧 TCP
连接自然排空，UDP 会话按 reconnect-only 语义切到候选代。切流前失败必须恢复旧配置和
旧接入；切流后由私有双进程状态
跨 Agent 重启继续排空，不得伪造 Xray 二进制发布回执。启用 Beta 后的配置交接采用
`handoff-force`：默认等待 120 秒，超时后先做最终计量采样，再终止上一代；已接管的新代继续
承载新连接。若节点上还留有上一张配置单的双进程状态，Agent 必须先按同一规则收口上一代，
存在可执行的新配置单时无需再等旧单剩余的排空时间；清除运行态后下一轮才领取新配置，禁止
叠出第三代。候选使用目标 API 完整地址（IP 与端口）、splice 模式和完整授权快照；新增入站必须先恢复授权
再接入，删除入站不得被旧授权快照阻止。直接监听的 API/metrics 也要纳入清单和 admission
barrier；使用该能力需要 Xray 明确报告 `control-listener-handoff-v1`。继承 FD 的地址、inode、cookie、
协议和实际 socket 配置摘要仍必须核验。缺少交接能力/manifest 或运行代不能提供完整交接证明时，
v40 可在候选预检与最终计量成功后走普通重启/回滚路径。真实端口冲突、候选配置错误、授权
检查点缺失/损坏或计量落盘失败不能当作能力不足忽略；切流前优先恢复旧进程，已开始的双进程
失败保留身份检查点，由本地恢复收口，禁止新建第三代。配置降级原因保存到本地运行对账记录，
二进制降级原因保存在原尝试回执；策略仍回显批准值，避免改写历史。

Agent 的 API 就绪、授权、转发恢复和统计共用配置端点，支持 IPv4/IPv6 loopback。
优先读取 `api.listen`，否则读取 `api.tag` 指向的 inbound（默认标签 `api`）；
通配绑定只在连接时映射为同地址族 loopback，不能把 IPv6 API 截成端口后拨 IPv4。

Agent 的本地 Xray gRPC 只读调用遇到阻塞 socket 的读等待超时（Linux 常见为
`EAGAIN` / `Resource temporarily unavailable`）时，优先内部重新连接并重试；最多
3 次、合计最多 10 秒，保留单次 I/O 5 秒上限。v40 在双代期间将后台计量/转发观察缩为
共享 1 秒预算，执行后观察缩为共享 2 秒预算；执行锁覆盖该短观察和计量代次提交，随后在回执持久化/交付前释放。启动就绪检查同时受外层 deadline 约束，
碎片帧或 PING 不会刷新总预算。仅显式列出的查询可重试，统计请求带 `reset=true`、
连接/写入失败、EOF、协议错误和未知方法均不走该路径。变更请求超时不直接重放；
沿用上层读取实际授权/转发集合、只补差异的恢复逻辑。成功恢复输出
`XRAY_API_RETRY_RECOVERED` 安全元数据；最终失败保留首错阶段、errno、次数和耗时，
不记录请求/响应正文或授权凭据。该行为仅需更新 Agent，不改变 Console/Agent 协议。

v40 对代际控制的连接阶段也设置 2 秒超时，避免冻结进程的满 accept 队列永久阻塞守护线程。
读失败包含操作、PID 和超时上限；EOF 单独报告提前关闭，不把遗留 errno 当作当前原因。
候选已经退出时立即结束监听等待；重启恢复中的新进程按独立身份核验，不受已退出候选的等待判据影响。
控制失联时先持久记录恢复决定并冻结配置/授权/计量身份：若已接流候选健康，仅退役旧代并
提升共享计量 writer；否则按批准目标重启并恢复动态状态。失败回执与恢复成功回执保留次序。
两条恢复路径与普通收敛共用互斥锁，锁内动作开始前重新读取当前检查点，避免守护已完成恢复
而主线程仍使用过期副本报错。回退旧 Agent 前先完成新格式的本地恢复检查点。
连续发布结束后的旧代可执行文件和日志回收策略见 `docs/concepts.md`；现场不要按目录时间直接删除
正在使用的映像。自动回收仅处理已确认不再存活的受管代，错误会保留现场并记录。

配置交接在暂停旧代前，把完整候选授权冻结到私有 `xray-config.candidate-grants.json`。
未管理授权时也要先冻结本地授权，不把“恢复时再读取正式文件”留到中断之后。
旧代丢失时，配置候选只能从此快照恢复动态授权并读回核验，完成后才 `seal`/`resume`；
二进制候选仍沿用正式 `grants.desired.json`。缺失、旧格式 `null`、损坏或不安全的快照
不得被解释成空数组；保持候选暂停、保留检查点并报告错误，等待修复后重试。
完整空数组 `[]` 与每个入站的空用户列表均为明确目标，不回退到旧授权。已 `seal`
但尚未接入的配置候选，守护线程也必须确认完整快照可读才恢复 admission。
新代接入后才提交正式授权，交接结束再清理临时文件；已接入的旧版运行态允许保留其
原有“没有完整候选快照”的兼容语义，不因此中断现有连接。

候选接入并关闭旧 UDP 后，使用 fenced `drop_tcp` 关闭旧代 public/control 监听描述符，
而不是保持端口绑定到旧连接排空；已接受的 TCP 连接和旧 REALITY cover 保留。候选通过
直接子进程启动，监听 FD 只在 Xray 子进程的 exec 前开放继承，日志进程与等待进程不得
持有监听 FD。首次启用这套能力时先更新 Agent，再经其二进制交接更新 Xray，以免旧启动
器的日志管道继续持有重复 FD；不能仅替换磁盘上的 Xray 文件。

## 授权发布

1. 区分“已保存”“已形成快照”“已下发”和“节点已执行”。
2. 已有授权单未落地时等待，不提前判断无需下发，也不修改已下发名单。
3. 暂停的授权单先由操作者处理；等待不计为失败重试。
4. 回滚以新的授权变更恢复先前主体集合，不能删除历史记录。

## Agent / Xray 二进制发布单

两类二进制共用发布单、逐机目标、逐次尝试和操作事件；不与配置/授权发布混用。
发布单冻结组件、构建标识、双架构摘要、操作者、范围与更新前摘要。`build_id`
是产物标识，数字 `id` 才是一次发布；重试保留原尝试证据，并增加 attempt。
每个组件最多一张活动单，支持停止和逐机重试，最多 32 次。停止不是回滚，已开始
执行的结果仍可回报；迟到的结果不重新激活发布，也不能覆盖后续尝试。

发布历史只保存元数据和证据，不保存历史二进制，不提供历史单内回滚按钮。
当前产物来源仍为 Console 内嵌文件；未来上传覆盖应接入同一当前产物目录边界，
本版没有上传入口。当前需要人工回退时，部署携带所需字节的 Console，再创建新单。
旧 Agent 的最后一次批准仅保留为只读迁移基线，不伪造逐机执行记录，也不再用于下发。
旧 Xray 发布保留原 ID、范围、摘要、结果和事件，已有执行证据单独标为迁移记录。

前端两页签复用相同组件和状态语义；概览仅在发布活动时轮询，历史按 20 条分页，
逐机尝试按需展开，事件按 200 条分页。选中全部机器也是批准时冻结的明确名单，
不会授权后来加入机队的机器。当前摘要相同只显示“已一致”，不等同某次发布成功。

产物下载地址带冻结的 `sha256`，当前字节变更时旧地址拒绝下载。更换 Console
不自动批准机队更新；活动单产物已不可用时停止该单，再基于当前产物创建新单。

### Agent 执行与验证

安装器和自更新先执行 `brocade-agent self-test`：成功退出且输出稳定行
`brocade-agent-self-test-v1` 表示当前可执行文件具备 Agent 入口。该命令不读凭据、不访问
控制面、不创建状态；它不等同运行时健康检查，正常轮询与收敛验证仍按下面的发布流程进行。
尚无此命令的旧 Agent 走兼容探测，读取未知命令的帮助输出中独立的 `run` 命令词，
不要求英文 `expected` 文案。自更新为每次探测设置 10 秒超时；v1 自检响应须持续兼容后续版本，
CLI 自检不改变 HTTP 协议版本。

Agent 发布页和新发布记录中的版本是最后一次修改 Agent 本地源码依赖闭包
（`brocade-agent`、`brocade-probe`、`brocade-deployment`、`brocade-core`）的完整 Git
提交号；只有这些路径未提交时才追加 `-dirty`。Console、前端和文档提交不会推进这个
版本。它只供人追溯来源，不能替代 `build_id` 或每架构 SHA-256：依赖解析、工具链或
构建配方仍可能在源码提交不变时改变字节，机器是否需要升级始终按实际摘要判断。

1. 先验证 Console/Agent 协议兼容和目标 Agent 的自更新能力。
2. 使用灰度和有界批次，观察版本、摘要、轮询、运行上报和收敛债务。
3. 节点失联、摘要不符或协议能力不足时停止推进，不把未知状态视为成功。
4. 需要回退时按相同发布机制分发已知良好的旧字节，并保留新发布记录。

新 Agent 在原子替换前复查批准、保存单条持久回执，重启后重试上报。只有已安装
和运行摘要都为目标、目标进程重新轮询且运行上报新鲜才确认成功。旧进程不能替新
进程确认成功。旧 Agent 首次跨入本版缺少替换回执时，以相同运行验证标为“观测确认”；
已声明回执能力却丢失回执不能算成功。能力通过可选 header 协商，当前 Agent 协议版本为 45，
最低兼容仍为 20，不因新增审计字段强制隔离旧机队。失败后未替换的原进程继续工作，
不增加 Agent 自动回滚脚本。失联或回执过期由人工判断，不能自动视为成功。

## Xray 发布

平滑交接从目标领取工单的 `dispatched_at` 起计算一小时整体执行期限。单步下载、预检、启动
或 RPC 失败仍立即报告真实失败；一小时到期但没有终态回执时，Console 只把该目标标为
“整体执行超时”，不会据此终止进程、重启 Xray 或解除节点本地的交接互斥。同一次尝试稍后
到达的终态回执仍会被接受；操作者显式重试后，旧尝试才由 attempt fencing 隔离。
如果节点仍上报同一 release/attempt 的双进程交接运行态，Console 和 Store 都禁止重试，避免
把尚在排空的尝试错误地隔离。只有该运行态清除后，超时目标才可由操作者创建下一次尝试。

新建 Xray 二进制发布提供“直接重启”和“双跑交接 Beta”两个选项，默认选择直接重启
（`restart`），会立即中断现有连接，停止旧进程后启动新版本；该路径不携带排空期限。
只有设置中启用交接 Beta 才允许新建双跑交接发布，后端也校验；开启后默认仍为直接重启。
双跑交接须显式选择（`handoff-force`）：新代接管后，旧连接默认最多等待 120 秒，
到期先完成最终计量采样，再强制退役旧代并中断剩余连接；批准前会提示并确认这一影响。
排空期限可配置 10..=86400 秒。页面不再提供普通 `handoff`；历史发布和既有 API 协议保留
该值的兼容语义，按原批准期限到时转为阻塞并继续保留旧连接。API 仍要求明确提交策略与
排空期限，既有发布沿用批准时冻结的设置。双进程状态存在期间，
Agent 不领取配置或授权工单，避免结构变更破坏交接。pause/export/恢复动态状态/resume 的短
切流区间与动态转发和计量串行；之后立即释放锁。Agent 每个 15 秒收敛边界推进一次排空，
不在主循环同步等待整个排空窗口；排空完成后立即提交发布回执，下一轮恢复领取其他工单。
配置发布的交接分支（Beta 开启时）采用 `handoff-force`；已批准二进制发布不受后续关闭 Beta
影响，幂等重放和重试也不重新解释策略。协议 v32 留下的已过期配置 `handoff` 运行态仍按原
兼容路径收口。系统管理员仍可在节点或配置发布详情中对已过期的旧运行态执行
“强制完成交接”，命令只携带 deployment/claim generation，不接受来自控制面的 PID。

### 构建身份与可复现门槛

- Xray 发布页和新发布记录中的版本是最后一次修改 `components/xray-core` 的完整 Git
  提交号；只有该目录未提交时才追加 `-dirty`。上游 banner/安装兼容版本仍单独保留，
  Git revision 只负责追溯 Brocade fork 来源，不替代构建标识或每架构摘要。
- 编译器版本系列只有一个来源：`components/xray-core/.go-version`。CI 和 Console 构建共用其 major/minor 与最低安全补丁版本，允许同系列较新的补丁版本（例如 `~1.26.10`），并在产物记录中保存实际补丁版本；跨系列或无法解析的本地版本直接报错，可通过 `BROCADE_GO` 指向匹配的编译器。
- 编译配方由 `crates/brocade-console/build/xray.rs` 固定，隔离宿主机的 Go 默认参数、workspace、实验开关和 CPU 级别，关闭 VCS 和自动 PGO。Console 的 Git 提交号、前端变化不会注入 Xray 字节。
- 依据 Go 实际选择的生产源文件、汇编、嵌入资源、依赖及标准库计算输入指纹；包含未提交/未跟踪的生产文件，不把无关文档和测试当成数据面变更。源码在构建途中变化会报错重试。
- 每个 `OUT_DIR/xray-<arch>` 都有对应的 `.build.json`，记录源码指纹、精确编译配方、ELF 架构、大小和 SHA-256。构建日志打印路径与摘要；归档预编译文件时必须成对保存。CI 单独上传双架构记录。
- `BROCADE_XRAY_BIN_X86_64` / `BROCADE_XRAY_BIN_AARCH64` 不是绕过校验的入口：缺少配套记录、输入不匹配、架构错误或字节变化均失败。旧的裸二进制应取消 override，从当前源码重建；不要手填一份记录替它背书。未知记录仍须独立重编、逐摘要验证。
- 本机的 `target/brocade-xray-verified/records.json` 保存最近 128 组已验证输入及摘要，跨 Cargo profile 和 OUT_DIR 复用，锁与原子写保护并发。CI 缓存这份有界证据，不缓存 Xray 二进制。相同输入、不同摘要属于异常，立即中止，不能以删除基线来消除报错。
- 首次出现的输入会以独立 Go 缓存再编译一次并比较字节摘要；清理 `target/`、更换构建机、CI 缓存失效或旧记录超过保留上限后也执行此检查。这只能证明本次可复现，不能代替已丢失的历史证据。记录不是签名证明，不能防范已被控制的构建主机；生产发布仍以冻结的实际字节和灰度验证为准。

只改 Console/前端时，核对本次双架构摘要与上次发布记录一致。若确有 Xray 源码、依赖、编译器或配方变更，先审查输入差异，再按下面步骤单独批准 Xray 发布；部署 Console 本身不自动升级机队。

### 节点发布与回滚

1. 冻结目标双架构摘要和每台机器更新前摘要。
2. 只能批准正在运行受管 Xray 的机器；每台都必须真实替换并启动目标字节。
3. 下载必须校验大小上限、摘要、版本和当前配置；替换发生在收敛安全边界。
   API 端口先就绪不代表业务已经恢复。Agent 必须确认 API 由本次受管 Xray PID 持有，
   立即从节点本地快照恢复动态转发与授权并读回验证；配置内静态监听最多再等待 5 秒。
   不能等待下一次 15 秒控制面对账才补业务。
4. 基础进程、受管摘要或配置内监听失败时恢复冻结的旧二进制，并将该机器标为需处理。
   只有动态转发或授权部分失败时保留已经恢复的新进程和业务，不再用第二次重启扩大中断；
   节点写入本地 degraded 标记、每秒重试本地恢复，发布保持 `failed-dirty`，完整后才能把
   同一 attempt 结算为成功；原始异常回执保留在事件审计中，页面显示“自动恢复完成”。
   已按授权的 `handoff-force` 等待期限退役旧进程并成功验证目标版本时，发布页和历史统一显示绿色
   “已升级”，不再提示预期的排空超时。是否强制退役仍由回执字段留存，不能据此宣称旧连接无损。
   双跑模式批准时只确认等待期限和到期断开旧连接的规则，使用普通“确认升级”，不将正常到期处理
   表述成异常或破坏性失败；直接重启仍明确提示立即中断连接。
5. 部署携带旧 Xray 的 Console 后，仍需创建一条新的 Xray 发布；不要修改历史发布。

节点将最后一份完整转发期望保存为 `forwarding-desired.json`，将实际确认安装集合单独保存为
`forwarding-applied.json`；部分失败只能缩小后者，不能覆盖前者。授权恢复使用
`grants.desired.json`。首次升级到这一实现时，如尚无完整转发期望文件，可从旧版已确认安装
检查点迁移一次。Agent 启动、受管 Xray PID 变化、配置重启、二进制更新和回滚都走同一恢复
入口；Console 暂时不可达不影响节点先恢复最后已知可用状态，随后正常对账再纠正到权威状态。

配置发布的新配置若在暂停旧代前校验失败，旧进程保持不动；交接切流前的启动、动态恢复或
基础健康失败，Agent 原子恢复上一份配置并恢复旧代接入。候选代接入后持续健康时，
保留双进程证据继续排空；不满足交接条件的重启路径若启动失败，仍恢复上一份配置并执行
同一动态恢复流程。配置已经健康、只有动态状态不完整时不回滚配置，避免为了短暂一致性再次
中断当前已恢复的连接能力。

交接候选进程死亡且旧代已经关闭 UDP，或交接两代都死亡时，Agent 每秒守护会自动进入
崩溃恢复。先持久化私有 `xray-crash-recovery.json`，核验冻结的候选摘要、配置、授权和计量
命名空间，再终止残留旧代并从受管路径重新启动；残留 TCP 连接会中断。此路径不等待 Console，
也不等待两分钟排空期限。正常健康交接仍按所批准策略退役，不因本恢复路径提前终止。

恢复沿用两份共享计量文件，在所有写入进程退出后校验和同步，保持累计值与 epoch；崩溃前后
未知时段不能认证为零流量。配置发布必须使用完整候选授权快照，包括显式空数组；摘要不符、
快照缺失或损坏、未知进程或计量损坏均保留检查点并报错。恢复业务接入前恢复动态转发与授权并验证
全部监听，成功后才清理交接。Agent 在启动中退出后可接管已启动的恢复代；恢复代再次死亡
仍沿用原计量命名空间重试。失败后等待 5、10、20、40、60 秒，重试等待上限为 60 秒。

使用共享计量的进程在旧 writer 退出、新 writer 尚未确认时必须暂停采样并报错重试，
不能退回进程 epoch。新 writer 确认后继续使用原 journal epoch，下一次累计读数包含等待期间
的真实增量。只有未配置该 journal 的旧版进程可以使用进程 epoch。Console 对旧 Agent 上报的
「journal 身份退回到已经运行的进程」保留原计数头并拒绝该计数，避免再次计入历史绝对值；
在上次读数之后实际启动的旧版进程仍按正常重启记账。

若需修复历史重复用量，先保全原始读数与回执，按真实入账顺序处理同秒 no-op，
只对证明为同一 journal 连续累计值的窗口扣除重复前缀。接入与中继明细、用户日汇总、
机器日汇总/窗口、用户机器/入口归属必须在同一事务中修正，并核验真实增量守恒。
只在整日明细仍完整保留时重建该日缺口标记。保留操作前后影像及唯一冲正 ID；
不得修改原始读数、回执、计数头或通过整库恢复覆盖后续流量。

二进制发布的崩溃与恢复分别保存到有界私有 `xray-crash-report.json` 和
`xray-crash-recovered-report.json`，按崩溃、原发布回执、恢复成功顺序补报，避免离线恢复覆盖
失败证据；同一 attempt 成功后仍保留原始失败审计。崩溃恢复不冒充排空期限触发的强制退役。
配置崩溃恢复保留配置发布身份，不生成二进制发布回执。

## 完成条件

- 每个目标都有明确终态，未知、失联和隔离待补偿没有被统计为成功。
- 发布事件、摘要、操作者动作和验证证据可审计。
- 按相应发布域的成功判据核验运行与业务结果；自动波次按既定策略推进。
- 后续动作和遗留风险已记录，没有依赖口头记忆。
