# 发布与回滚手册

## 先识别发布域

| 发布域 | 主要风险 | 正确回滚方式 |
| --- | --- | --- |
| 模型配置 | 节点配置变化、服务重启、链路中断 | 以历史修订为目标创建新发布，不改写历史 |
| 用户授权 | 访问主体变化 | 提交反向授权变更并形成新的可审计任务 |
| Agent | 收敛逻辑和协议兼容 | 将已知良好的字节设为当前产物，再创建新的发布单 |
| Xray | 数据面兼容、进程健康、链路中断 | 执行失败时本地恢复原字节；人工回退需创建新的发布单 |
| Console | API、数据库、嵌入资源和控制面可用性 | 按 `console-deployment.md` 回滚二进制；先确认数据库兼容 |

不要为了复用操作流程合并这些发布域。一次 Console 部署不会自动更新节点 Agent 或 Xray；配置发布与授权发布的风险和代价也不同。

## 通用发布门槛

发布前必须能够回答：

- 发布对象和不可变标识是什么？
- 影响哪些节点、用户、链路或控制面实例？
- 灰度对象如何选择，成功信号是什么？
- 什么条件会暂停、熔断或回滚？
- 回滚会产生新的审计记录，还是替换宿主机二进制？
- 新旧协议、配置和数据库是否兼容？
- 哪些检查已实际运行，哪些因环境限制未运行？

没有明确答案时只做预检，不开始外部变更。

## 配置发布

1. 确认草稿基线和目标修订，检查预览产物与影响范围。
2. 审查破坏性操作、波次、节点隔离和授权差异。
3. 从低风险灰度开始，观察下发、收敛、健康和拨测结果。
4. 只有当前波次满足成功判据才继续；失败或状态不确定时暂停。
5. 回滚时选择已知良好的历史修订创建新发布，保留原发布和失败事件。

## 授权发布

1. 区分“已保存”“已形成快照”“已下发”和“节点已执行”。
2. 已有授权单未落地时等待，不提前判断无需下发，也不修改已下发名单。
3. 暂停的授权单先由操作者处理；等待不计为失败重试。
4. 回滚以新的授权变更恢复先前主体集合，不能删除历史记录。

## Agent / Xray 二进制发布单

两类二进制共用发布单、逐机目标、逐次尝试和操作事件；不与配置/授权发布混用。
发布单冻结组件、构建标识、双架构摘要、操作者、范围与更新前摘要。`build_id`
是产物标识，数字 `id` 才是一次发布；重试保留原尝试证据，并增加 attempt。
每个组件最多一张活动单，支持停止和逐机重试，最多 32 次。停止不是回滚，已开始
执行的结果仍可回报；迟到的结果不重新激活发布，也不能覆盖后续尝试。

发布历史只保存元数据和证据，不保存历史二进制，不提供历史单内回滚按钮。
当前产物来源仍为 Console 内嵌文件；未来上传覆盖应接入同一当前产物目录边界，
本版没有上传入口。当前需要人工回退时，部署携带所需字节的 Console，再创建新单。
旧 Agent 的最后一次批准仅保留为只读迁移基线，不伪造逐机执行记录，也不再用于下发。
旧 Xray 发布保留原 ID、范围、摘要、结果和事件，已有执行证据单独标为迁移记录。

前端两页签复用相同组件和状态语义；概览仅在发布活动时轮询，历史按 20 条分页，
逐机尝试按需展开，事件按 200 条分页。选中全部机器也是批准时冻结的明确名单，
不会授权后来加入机队的机器。当前摘要相同只显示“已一致”，不等同某次发布成功。

产物下载地址带冻结的 `sha256`，当前字节变更时旧地址拒绝下载。更换 Console
不自动批准机队更新；活动单产物已不可用时停止该单，再基于当前产物创建新单。

### Agent 执行与验证

Agent 发布页和新发布记录中的版本是最后一次修改 Agent 本地源码依赖闭包
（`brocade-agent`、`brocade-probe`、`brocade-deployment`、`brocade-core`）的完整 Git
提交号；只有这些路径未提交时才追加 `-dirty`。Console、前端和文档提交不会推进这个
版本。它只供人追溯来源，不能替代 `build_id` 或每架构 SHA-256：依赖解析、工具链或
构建配方仍可能在源码提交不变时改变字节，机器是否需要升级始终按实际摘要判断。

1. 先验证 Console/Agent 协议兼容和目标 Agent 的自更新能力。
2. 使用灰度和有界批次，观察版本、摘要、轮询、运行上报和收敛债务。
3. 节点失联、摘要不符或协议能力不足时停止推进，不把未知状态视为成功。
4. 需要回退时按相同发布机制分发已知良好的旧字节，并保留新发布记录。

新 Agent 在原子替换前复查批准、保存单条持久回执，重启后重试上报。只有已安装
和运行摘要都为目标、目标进程重新轮询且运行上报新鲜才确认成功。旧进程不能替新
进程确认成功。旧 Agent 首次跨入本版缺少替换回执时，以相同运行验证标为“观测确认”；
已声明回执能力却丢失回执不能算成功。能力通过可选 header 协商，协议版本仍为 24，
最低兼容仍为 20，不因新增审计字段强制隔离旧机队。失败后未替换的原进程继续工作，
不增加 Agent 自动回滚脚本。失联或回执过期由人工判断，不能自动视为成功。

## Xray 发布

### 构建身份与可复现门槛

- Xray 发布页和新发布记录中的版本是最后一次修改 `components/xray-core` 的完整 Git
  提交号；只有该目录未提交时才追加 `-dirty`。上游 banner/安装兼容版本仍单独保留，
  Git revision 只负责追溯 Brocade fork 来源，不替代构建标识或每架构摘要。
- 编译器精确版本只有一个来源：`components/xray-core/.go-version`。CI 和 Console 构建共用；本地版本不符直接报错，可通过 `BROCADE_GO` 指向匹配的编译器。
- 编译配方由 `crates/brocade-console/build/xray.rs` 固定，隔离宿主机的 Go 默认参数、workspace、实验开关和 CPU 级别，关闭 VCS 和自动 PGO。Console 的 Git 提交号、前端变化不会注入 Xray 字节。
- 依据 Go 实际选择的生产源文件、汇编、嵌入资源、依赖及标准库计算输入指纹；包含未提交/未跟踪的生产文件，不把无关文档和测试当成数据面变更。源码在构建途中变化会报错重试。
- 每个 `OUT_DIR/xray-<arch>` 都有对应的 `.build.json`，记录源码指纹、精确编译配方、ELF 架构、大小和 SHA-256。构建日志打印路径与摘要；归档预编译文件时必须成对保存。CI 单独上传双架构记录。
- `BROCADE_XRAY_BIN_X86_64` / `BROCADE_XRAY_BIN_AARCH64` 不是绕过校验的入口：缺少配套记录、输入不匹配、架构错误或字节变化均失败。旧的裸二进制应取消 override，从当前源码重建；不要手填一份记录替它背书。未知记录仍须独立重编、逐摘要验证。
- 本机的 `target/brocade-xray-verified/records.json` 保存最近 128 组已验证输入及摘要，跨 Cargo profile 和 OUT_DIR 复用，锁与原子写保护并发。CI 缓存这份有界证据，不缓存 Xray 二进制。相同输入、不同摘要属于异常，立即中止，不能以删除基线来消除报错。
- 首次出现的输入会以独立 Go 缓存再编译一次并比较字节摘要；清理 `target/`、更换构建机、CI 缓存失效或旧记录超过保留上限后也执行此检查。这只能证明本次可复现，不能代替已丢失的历史证据。记录不是签名证明，不能防范已被控制的构建主机；生产发布仍以冻结的实际字节和灰度验证为准。

只改 Console/前端时，核对本次双架构摘要与上次发布记录一致。若确有 Xray 源码、依赖、编译器或配方变更，先审查输入差异，再按下面步骤单独批准 Xray 发布；部署 Console 本身不自动升级机队。

### 节点发布与回滚

1. 冻结目标双架构摘要和每台机器更新前摘要。
2. 只能批准正在运行受管 Xray 的机器；每台都必须真实替换并启动目标字节。
3. 下载必须校验大小上限、摘要、版本和当前配置；替换发生在收敛安全边界。
   API 端口先就绪不代表所有业务监听已就绪；更新路径最多再等待 5 秒检查全部监听，
   超时或无法检查仍失败，不跳过健康检查、授权恢复或运行摘要校验。
4. 健康检查失败时恢复冻结的旧二进制，并将该机器标为需处理。
5. 部署携带旧 Xray 的 Console 后，仍需创建一条新的 Xray 发布；不要修改历史发布。

## 完成条件

- 每个目标都有明确终态，未知、失联和隔离待补偿没有被统计为成功。
- 发布事件、摘要、操作者动作和验证证据可审计。
- 观测窗口足以覆盖重启、轮询、收敛和拨测周期。
- 后续动作和遗留风险已记录，没有依赖口头记忆。
