# 事故响应手册

## 原则

先保护数据面和证据，再恢复控制面便利性。不要通过删除数据库、改写修订、清空 Agent 状态、批量重启或绕过摘要校验来获得短暂的“绿色”。所有生产变更都需要明确目标和授权。

## 1. 建立时间线

记录发现时间、受影响范围、最近部署/发布、告警来源、操作者动作和当前假设。时间统一使用带时区的 ISO 8601。日志摘录不得包含凭据、完整订阅或用户流量内容。

## 2. 判断故障域

- Console：健康检查、登录、API、数据库连接、后台任务。
- Store：事务冲突、连接池、约束、配额、发布或授权状态。
- Agent：轮询新鲜度、期望状态、收敛债务、本机服务与离线缓冲。
- Xray：受管路径、运行摘要、配置预检、重启和健康检查。
- 网络/探测：Console 拨测、节点探测、DNS、TLS、反向代理和路径 MTU。
- 前端：静态资源/API 版本错配、路由、缓存或用户可见状态。

## 3. 只读采证

Console 主机的常用入口：

```sh
sudo systemctl status brocade-console
sudo journalctl -u brocade-console -n 200 --no-pager
curl --fail https://console.example.net/healthz
sha256sum /opt/brocade/brocade-console
```

同时保存当前发布 ID、修订、目标状态、Agent/运行版本和摘要。数据库调查优先使用只读查询；需要锁表、修复或恢复时另行制定操作步骤。

### Agent 日志与缺失计量代次

使用独立 journal 的 systemd 节点须执行
`journalctl --namespace=brocade-agent -u brocade-agent -n 50 --no-pager`；
不带 namespace 可能只看到服务启动、退出记录，漏掉实际收敛错误。旧节点先通过
`systemctl show brocade-agent -p LogNamespace` 确认；OpenRC 日志入口见
[可观测性文档](../../docs/observability.md)。

`xray has no active usage generation` 表示运行中的 Xray 缺少本地 `usage-generation`
检查点，用量采样及配置、授权变更前的最终采样都会因此失败。先保留现场，对照
`node_agent_state.usage_generation_id`、已激活的 `usage_generation_activations` 和最后成功发布的
配置摘要、授权及计量归属；不能直接写入最新或失败发布的代次。
仅当实际运行态与该已激活代次一致时，才在节点收敛锁保护下以私有权限原子恢复检查点，
同步文件和目录后确认用量上报被接受，再通过正式 API 逐台重试。状态无法证明一致时停止修复，
不要清空计数器、计量 journal、usage cursor 或跳过最终采样。已取消的历史单保持终态，
先检查当前配置差异和有效工单，避免重新执行已经被后续操作替代的目标。

### Agent HTTP 响应超时

Agent 的 HTTP/HTTPS 客户端按 [RFC 9112 §6.3](https://www.rfc-editor.org/rfc/rfc9112.html#section-6.3)
识别正文边界：Content-Length 按字节读满即返回；chunked 需完整零块、trailer 与终止空行；
HEAD、204、304 不读取正文；100/103 等临时响应之后继续读取最终响应。只有未声明长度的
响应等待连接关闭，不能因为正文恰好是合法 JSON 就判断已收齐。

截断长度、缺失 chunked 尾部、冲突 Content-Length、同时声明 Transfer-Encoding 与
Content-Length、不支持的传输编码会显式失败。头部、临时响应、chunk 元数据、trailer 与正文
共用原有 16MiB 总报文预算。仍兼容 TLS 对端省略 close_notify，但不能因此接受截断的定长或
chunked 正文。该修复不延长网络超时、不自动重放 HTTP 请求；仅需更新 Agent，无协议变更。

协议 v39 起还记录 `phase`、已知 HTTP `status`、`received_bytes`、`content_length` 和
`response_elapsed_ms`，不包含响应头值、正文或凭据。先据此区分未收到状态行、头部不完整、
正文停顿或关闭分隔响应等待 EOF，再结合代理访问日志判断链路位置；不能只凭超时认定
Console 执行慢。派发响应丢失后的重领与新旧版本兼容行为见 `../../docs/concepts.md` 的节点收敛说明。

### 停机后 Ping 持续没有新数据

先分别检查 `node_ping_probe_samples` 的最新采样时间、Agent 独立 journal 中的探测结果和
`/agent/v1/ping-probe` 上报响应。本机探测正常但上报反复返回 `PING probe clock skew`，
且请求年龄接近 900 秒、机器实际时钟正常时，应排查旧 Console 把补报年龄误当作
超过 10 分钟时钟偏差，造成队首反复重试。修复后的 Console 按 Ping 的数据保留策略接收
历史补报，超期有效样本成功确认并计入 `skipped_samples`；异常未来时间仍拒绝。
只更新 Console 即可让已有 Agent 继续排空队列，不依赖某个固定的离线时长。
验证时同时确认历史补报正在推进、最新采样时间追上当前时间，不能只看上报返回 200。
现有 Agent 缓存有限，长停机期间已过期或进程重启丢失的样本仍应显示真实缺口。

### Xray 平滑交接控制失联

核对 `xray-upgrade.json` 中的旧代/候选 PID、start ticks、摘要、phase 与实际进程，保留
`xray-crash-recovery.json`、配置候选授权快照和共享计量文件。v40 的控制错误包含 operation、
连接/响应阶段与 2 秒上限；`Resource temporarily unavailable` 代表有界等待超时，不能
仅据此判定配置错误。候选被 kill 时不应等满 30 秒启动窗口；被冻结或控制 socket 丢失时，
守护线程应在本地恢复，期间用实际业务请求校验可用性，不把 15 秒发布收尾轮询当作断流时长。
健康候选可继续服务时只清理失联旧代；重启降级会中断连接，需核对降级原因、完整授权/转发
恢复及计量 epoch 延续。不要删除交接/恢复文件来绕过围栏，也不要同时启动第三个 Xray。

可重复 Docker 注入入口及覆盖边界见[交接故障验证](../../scripts/tests/xray-faults/README.md)。

### SS2022 中转配置启动后回滚

配置切换为 SS2022 后报 `handoff listener group is incomplete, unsupported or closed`，
先对照候选 `xray.next.json` 的 `settings.network` 和失败代际 `manifest.json` 的监听清单。
SS2022 中转使用 `tcp,udp`，即使 `streamSettings.network` 为 `tcp`，也会在同一端口开启
原生 UDP 监听。旧 Agent 只按传输层识别 TCP，漏登 UDP，导致 Xray 拒绝 seal 并恢复旧配置。
更新包含此修复的 Agent 后重试原配置发布；此问题不需要修改密钥、模型修订或升级 Xray。
验收须确认清单和运行状态同时包含该端口的 TCP、UDP，且代际已 ready、accepting。

### HY2 时间戳程序加载失败

若预检报 `HY2 时间戳程序加载失败`、`Permission denied (os error 13)`，且 verifier 日志包含
`BPF_ST stores into R1 ctx is not allowed`，说明旧 Agent 用立即数存储指令写入 BPF 上下文，
被 Linux 6.1 等内核拒绝。这条明确的 verifier 错误不是缺少 root 权限；增加 capability 或
关闭安全策略无法修正指令。更新包含寄存器存储修复的 Agent 后重试，无需修改 Xray、配置或授权。
该预检在停止旧 Xray 前执行，失败时保留旧服务。若没有上述 verifier 日志，则应另查实际的
BPF 系统调用权限与容器安全策略，不能只凭 `Permission denied` 判断为同一缺陷。

### HY2 升级后误报过滤器占用

Agent 从立即数存储改为寄存器存储后，程序指纹会改变。只认可新版指纹的 Agent 会把
仍在工作的旧版 `brocade_hy2_ts` 误报为“时间戳过滤器位置已被其他规则占用”；后续 Xray
重启重建私有链路可让报错消失，但 Agent 升级兼容缺口仍然存在。

更新包含新旧参考程序核验的 Agent 后，巡检会保留已验证的等效旧过滤器，无需重启 Xray；
新安装或过滤器丢失时统一安装寄存器存储版本。新旧指纹均从当前节点内核加载固定参考程序
取得，不能套用另一内核或构建机的 tag。旧参考只在现有过滤器与新版指纹不同时加载，
Linux 6.1 上的新安装和正常巡检不依赖旧指令支持。有效旧版可以持续复用，不为统一版本主动替换。

识别以已知等效程序指纹和实际生效路径为准，兼容缺失或不同的名称注释、handle 标签、默认
chain 省略，以及 tc 的数字表示差异。只检查 chain 0 的 pref 1 入口，其他 chain 的规则允许
共存，也不能代替入口规则；目标入口须为覆盖全部协议、启用软件执行的 direct-action BPF。
入口缺失才补齐；观察不完整、程序尚未识别、覆盖不足和实际规则冲突分别报明原因并保留现场，
不把无法确认当作正常，也不删除或覆盖现有规则。参考程序只在读取到需要核验的目标规则后加载。

### 机器尖峰流量归属

从「用量 → 实时 → 机器弹层」定位所选区间内的尖峰，拖选图表或在「统计 → 自定义」输入 UTC+8
起止时间。历史图与流入、流出共用区间；当天／当周／当月按 5 分钟／15 分钟／小时绘制已观测窗口均值，缩小自选区间可查看更细粒度。历史窗口过期后留空，日账本无法恢复速率走势。流入按采样窗口起点汇总（通常 30 秒），点击用户打开流入明细，用「合计／下行／上行」切换
排行并复制来源 IP。每行是一个来源地址，跨链使用时条形按接入链分段，点图例只看一条链；未记录
来源和端口转发保留独立合计，不会把链总量复制到多个 IP 行，也不会按时长均摊。只读账号看到的是
脱敏地址，同形的掩码逐行保留，不能据此认定为同一来源。

来源观测需新版 Console、Agent、Xray 及启用在线来源统计，只能从采集启用后记录。30 秒来源窗口
默认保留 24 小时，来源日汇总默认保留 31 天，可在数据保留设置中调整。日/周/月用日汇总；
自选分钟区间依赖窗口明细，过期、容量限制、断线和进程切换遗漏明确显示不完整，缺数不表示零。
来源与计费是独立采样；接入归属或采样窗口存在差异时，表格显示差异及账本值，无法确认接入归属的
余量合并到未归属行，避免跨链重复计算；不回写账单。

流出目标仍按小时保存，自选区间会扩大到覆盖所选时段的小时并标明实际范围；域名/IP 明细还受
其独立保留期和 Top-N 限制。当前不能把来源 IP 与目标排行认定为同一条连接；中继和落地机器
也不提供最终用户身份，应回到链头入口排查。生产升级前参考 `console-deployment.md` 的来源观测表兼容步骤。

### 草稿预览或提交卡住

先区分连接池等待、事务锁等待与编译计算。若 PostgreSQL 的死锁图同时出现
`pg_advisory_xact_lock(1112687438,65)` 和 `control_state ... FOR UPDATE`，检查模型写入口
是否统一先取得网络资源锁、再取得模型行锁。预览最终回滚也会在执行期间持锁，不能把它当作
普通只读查询。公共模型取锁入口覆盖预览、提交、直接编辑、回滚及纳管；底层操作再次取得
同一事务锁不改变此顺序。不要用增加连接池或无限重试代替修复反向取锁。

## 4. 控制影响

- 单节点异常优先隔离该节点，并保留其收敛债务与现场状态。
- 发布异常优先暂停或熔断相关发布，不唤醒更多目标。
- 授权异常先确认服务端保存、任务、下发和节点执行四个阶段。
- Console 部署异常按 `console-deployment.md` 判断能否安全回滚。
- Xray 健康失败使用发布中冻结的旧摘要，不从不明来源下载替代二进制。

## 5. 恢复与验证

选择最小、可审计、可逆的动作。恢复后至少观察一个完整的轮询、收敛和指标窗口，并用真实健康信号而不是单一进程状态判断完成。

## 6. 复盘

记录根因、促成条件、检测缺口、缓解动作、恢复证据和后续负责人。稳定的架构决策写入 `../adr/`；可重复的操作改进本 Runbook 或相关 Skill；一次性时间线不要变成永久 Agent 规则。
