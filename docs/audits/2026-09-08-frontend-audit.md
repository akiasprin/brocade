## P1：优先修复

### F01 · 提交清空了没有提交的新编辑

- 位置：`frontend/src/forge/draft-bar.tsx:39`、`:42`；单条丢弃按钮在 `:87`。
- 复现：草稿 A 点击提交，暂不返回请求；在其他面板保存草稿 B；提交 A 成功。
- 实际：请求体只有 A，成功回调却调用 `draft.clear()`，A、B 一起消失。B 没有写入服务端，也不再保留在本地。
- 根因：清理以响应时的整个草稿为对象，没有记录提交批次。`busy` 只锁住部分草稿栏按钮，不锁住所有编辑入口；展开列表里的单条“丢弃”也没有锁定。
- 建议：提交时固定批次及每条版本，成功只移除仍与该批次相同的条目；同一对象在等待期间的新修改必须保留。提交中的丢弃行为也要统一语义。
- 验收：等待期间新增 B、修改 A、切换页面分别测试；成功后只移除真正提交的内容，失败后全部保留。

### F02 · 多标签页草稿最后写入者覆盖前者

- 位置：`frontend/src/draft.ts:379`、`:483`。
- 复现：同账号打开两个标签页，均恢复空草稿；A 保存一项；B 不刷新页面再保存另一项。
- 实际：两个标签页各维护自己的内存数组，却写同一个 localStorage key；没有处理草稿的 `storage` 事件。B 写入时覆盖 A 的持久化副本，A 关闭或刷新后丢失其修改。
- 影响：不仅是显示不同步，也包括一个标签页提交/清空后，另一个仍持有旧草稿并可能重新写回。
- 建议：明确选择每标签页独立草稿，或跨标签页共享并做版本冲突检测；不能静默用旧数组覆盖存储。
- 验收：双标签页分别新增、改同一对象、提交、丢弃、刷新；冲突应保留双方数据并可见。

### F07 · 保存响应覆盖用户继续输入的内容

- 位置：`frontend/src/panes/settings.tsx:1488`；同类实现见 `:2012`（Ping 设置）。
- 复现：站点名称改成 A，点击保存并延迟返回；在输入框继续改成 B；服务端返回保存后的 A。
- 实际：输入框变回 A，B 消失。输入框在保存期间仍可编辑，但 `onSuccess` 无条件 `setForm(saved)`。
- 范围：站点外观已自动化复现；Ping 的 `setForm(next)`、分发设置及日志设置的源数据重填也需要按同一标准逐项验收，不能仅修一个面板。
- 建议：对比“本次提交值、当前输入值、服务端规范化值”，只同步没有继续编辑的字段；或者在整个请求期间明确禁用该表单。
- 验收：延迟响应期间修改同一字段和另一字段，均不能悄悄丢失；保存失败也不能重置输入。

### F08 · Agent 范围按数量比较，可能误批准全部机器

- 位置：`frontend/src/panes/agent-release.tsx:53`、`:81`、`:90`。
- 复现条件：保存的指定 ID 集合与当前机器列表不一致，但长度相同。例如已保存 `[A,C]`，当前列表 `[A,B]`。机器列表在表单挂载后发生替换也可能产生这种状态。
- 实际：全选框显示选中，但 B 的行仍未选中；点击批准发送 `scope: 'all'`，即使请求的 `nodes` 里没有 B。
- 后端语义已核对：`crates/brocade-store/src/agent_release.rs:132` 的 `All` 对所有机器返回 true，不按 nodes 数组过滤。因此不能依赖后端忽略这种前端误判。
- 建议：使用 ID 集合比较，先处理已不存在的 ID；保留用户选择的范围语义，不让“数量恰好相等”自动扩大执行范围。
- 验收：等长不同集合、机器新增/删除、空机队、范围回显、选择全部后增加机器；界面选择必须与请求范围一致。

## P2：状态与操作可靠性

### F10 · 全局设置提交后回到旧值

- 位置：`frontend/src/forge/draft-bar.tsx:25`；`frontend/src/panes/settings.tsx:2240` 附近的基准选择。
- 复现：已提交 MTU 为 1420，草稿改成 1380；停在设置页点击顶部提交。
- 实际：提交成功、草稿清空后，表单回到 1420。`refresh()` 没有使 `['settings']` 失效，基准从草稿切回缓存中的旧 `/settings` 值。
- 影响：用户以为保存失败，继续保存其他段时也需要警惕旧基准参与组装完整设置。
- 建议：提交结果与所有受影响查询同步，包括 settings；审查“撤销未发布修订”是否也刷新 settings、certs 等派生数据。
- 验收：保存草稿后显示新值；提交后保持新值；丢弃草稿恢复服务端旧值；撤销修订显示撤销后的值，四种语义分别验证。

### F06 · 初次请求中的失效不会保证读到新草稿

- 位置：`frontend/src/forge/shell.tsx:124`、`frontend/src/api.ts:1908`。
- 复现：无缓存的 `['snapshot']` 首次读取 `/model/snapshot` 尚未返回时，新增或丢弃草稿，触发集中失效；随后旧请求返回。
- 实际：复现中没有发起第二次读取，旧响应成为 `['snapshot']` 的数据。仅调用 `invalidateQueries` 无法保证这类首次在途请求被替换。
- 影响：使用固定 snapshot key 的面板可能继续显示旧模型；那些使用草稿版本 key 或直接叠加草稿的区域又显示新值，形成同屏不一致。能持续多久取决于后续轮询/重挂载，不能一概说永久。
- 建议：统一将草稿版本纳入读取键，或明确取消旧代请求并重取；核对 preview 及其下游读取的代际一致性。
- 验收：分别延迟 committed/preview 请求，再新增、修改、丢弃草稿；任意返回顺序都只能显示最新代。

### F05 · 退出失败后又被自动登录回来

- 位置：`frontend/src/app.tsx:108`、`frontend/src/ui/login.tsx:9`、`:15`。
- 复现：`logoutAdmin()` 失败且原 cookie 会话仍有效；App 忽略错误，清空本地 session，挂载 Login。
- 实际：Login 又请求 whoami，成功即 `onLogin`，回到原身份。`suppressAutoPublic` 只抑制 public 自动登录，不抑制这条恢复路径。
- 验证边界：自动化验证了“Login 收到有效 whoami 就恢复”的下游行为；退出失败到挂载 Login 的上游为代码追踪，未向真实会话执行故障注入。
- 建议：区分初始恢复和主动退出后的登录页；退出失败应呈现可重试结果，不能静默恢复原身份。
- 验收：服务端 500、网络中断、撤销成功但响应丢失、访客退出分别验证。

### F03 · 非法路由编码可使应用启动异常

- 位置：`frontend/src/forge/route.ts:91`、`:192`。
- 复现：以 `#/nodes/node/%` 打开或刷新页面。
- 实际：直接 `decodeURIComponent` 抛出 URIError；启动路由解析在外壳初始化阶段执行，当前没有对应恢复分支。
- 建议：捕获解码异常，回退到安全列表页或明确显示无效地址。
- 验收：孤立 `%`、不完整 UTF-8 编码、有效中文/编码斜杠、缺失路径段，均不导致整页崩溃。

### F04 · 草稿恢复没有校验条目结构

- 位置：`frontend/src/draft.ts:394`。
- 复现条件：草稿存储为 JSON 合法但结构异常的数据，例如 `[{}]`。这属于损坏存储/迁移健壮性场景，不是正常编辑必现。
- 实际：恢复过滤只排除旧的 swap 操作，`{}` 仍被接受；`draft.ops()` 产生 undefined，消费端访问 `op.op` 抛 TypeError。
- 建议：校验容器、条目和操作结构，异常条目隔离并保留原始备份，提示恢复失败；不要声称 catch JSON.parse 就已经覆盖损坏恢复。
- 验收：未知操作、缺字段、null、非数组、部分合法部分非法；合法编辑尽可能保留。

### F09 · 订阅查询失败后内容区空白

- 位置：`frontend/src/panes/subscription.tsx:120`、`:205`；`frontend/src/ui/bits.tsx:66`。
- 复现：首次打开 URI 订阅弹窗时，修订列表查询失败且无缓存。
- 实际：没有处理 `revisions.error`，因为 revision 为空始终进入 Loading 分支；而当前 Loading 返回 null，因此不是明显的加载动画，而是空白内容区，没有失败提示。
- 建议：明确分开加载、失败、没有修订、订阅为空；先检查上游查询错误再判断 content 的 pending。
- 验收：修订接口 401/500、无修订、产物接口失败、随后恢复正常均给出正确反馈。

### F11 · 复制按钮未统一使用 HTTP 兼容实现

- 位置：`frontend/src/panes/users.tsx:302`、`frontend/src/panes/chains.tsx:1956`；可复用实现为 `frontend/src/ui/platform.ts:18`。
- 复现条件：通过非 localhost 的 HTTP 地址访问，环境没有 `navigator.clipboard`，或 Clipboard API 写入被拒绝。
- 实际：用户信息复制按钮直接调用 clipboard 并吞掉错误，点击无反馈；Encryption 公钥复制会提示手动复制，但同样绕过已有 fallback。其他采用 `copyText()` 的入口行为不同。
- 建议：统一调用 `copyText` 并根据返回结果提示成功/失败。
- 验证边界：代码路径确认，未在真实 HTTP 浏览器上操作剪贴板。
- 验收：HTTPS、HTTP IP、Clipboard API 拒绝、fallback 也失败，提示与实际复制结果一致。
